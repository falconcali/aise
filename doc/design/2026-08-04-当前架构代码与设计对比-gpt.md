# AISE 当前架构代码与设计对比

## 1. 文档定位

本文记录 AISE 当前代码与 [Architecture.md](./Architecture.md) 最终架构设计之间的对应关系和差距。

本文不是架构规范。发生冲突时，以 `Architecture.md` 为准。本文应随实现进度更新，用于回答：

- 架构设计中的职责当前由哪个类型承担。
- 哪些能力已经实现。
- 哪些能力只有骨架或部分实现。
- 哪些目标能力尚未实现。
- 当前实现是否存在违反最终架构的不安全路径。

对比基线：2026-08-03 workspace 代码；设计基线：Architecture.md v3.1。

---

## 2. 当前运行链路

```text
Story Client
      |
      v
aise-server::api::turn::run_turn
      |
      v
SessionRegistry::get
      |
      v
tokio::spawn
      |
      v
Session::lock_turn
      |
      v
AiseEngine::run_turn
      |
      v
TurnRuntime::run
      |
      v
Configured Pipeline Vec
      |
      v
TurnCommitter -> Store::commit_turn -> SqliteStore
      |
      v
TurnEventSink -> SseSink -> Story Client
```

代码中没有 `TurnAdmission` 或 `StoryTurnCoordinator` 类型。Story Turn 串行化目前由 `aise-server::session::Session::lock_turn` 承担。v3.1 设计要求由 `AiseEngine` 内部的 `StoryTurnCoordinator` 强制串行化，并删除 `Session::turn_lock` / `Session::lock_turn`；当前实现尚未迁移。

## 4. Turn 串行化

### 4.1 已实现行为

`Session` 持有 `tokio::sync::Mutex<()>` 类型的 `turn_lock`。HTTP Turn handler 在后台任务中获取该锁，并持锁执行完整的 `AiseEngine::run_turn`。

当前 API 创建 Session 时同时生成唯一 `StoryId`，Session 与 Story 是一对一关系。因此在当前单进程 HTTP 入口中：

- 同一 Story 的 Turn 串行。
- 不同 Story 使用不同 Session 锁，可以并行。
- 全局 LLM 调用仍受共享 `LlmLimiter` 限制。

### 4.2 与 v3.1 的差距

- `AiseEngine::run_turn` 是公开方法，核心库调用方可以绕过 `Session::lock_turn`。
- 串行化能力位于 HTTP Session 层，没有覆盖未来 CLI 或消息消费者入口。
- v3.1 要求新增 `StoryTurnCoordinator` 并注入 `AiseEngine`，由 `AiseEngine::run_turn` 内部获取 per-Story permit；当前不存在该组件。
- v3.1 要求删除 `Session::turn_lock` / `Session::lock_turn`，Session 定位为临时连接资源而非 Story 串行化所有者。
- 多实例部署之间没有共享锁、租约或 fencing token。
- Mutex 等待队列没有显式容量、超时和拒绝策略。
- Session 删除与正在执行的 Turn 没有统一生命周期协议。

## 5. 固定工作流与 Runtime

`aise-server::app::build_engine` 和集成测试当前使用相同顺序：

```text
TurnInitializer
    -> BaselineContextBuilder
    -> WriterPlanner
    -> ContextRetrievalPipeline
    -> CharacterThinkPipeline
    -> StoryGenerator
    -> ValidationPipeline
    -> TurnCommitter
```

当前 `TurnRuntime::new` 接受 `Vec<Box<dyn TurnExecutionPipeline>>`，因此调用方仍可重排、遗漏或增加 Pipeline。固定拓扑目前是 composition root 的约定，不是 Runtime 强制的不变量。v3.1 要求以命名字段的 `TurnPipelineSet` 替换任意 Vec，并验证每个对象 `TurnStage` 与字段匹配。

`ContextRetrievalPipeline` 和 `CharacterThinkPipeline` 总会被 Runtime 调用，再根据 `WriterPlan` 自行 no-op。v3.1 要求由 Runtime 根据请求集合决定是否执行可选阶段，跳过时不产生 `StageStarted`。

`StoryRepairer` 已有类型，但没有加入 Pipeline Vec；Runtime 也没有 Validation / Repair 循环。`StoryRepairer` 应作为 Validation 循环内的辅助 Pipeline，不是独立阶段。

## 6. Pipeline 返回值与错误

当前接口（`core::turn_pipeline`）：

```rust
#[async_trait]
pub trait TurnExecutionPipeline: Send + Sync {
    fn stage(&self) -> TurnStage;

    async fn execute(
        &self,
        ctx: &mut TurnExecutionContext,
    ) -> Result<(), AiseError>;
}
```

`TurnStage` 已是有穷枚举（`TurnInitializer`/`BaselineBuilder`/`WriterPlanner`/`ContextRetrieval`/`CharacterThink`/`StoryGenerator`/`Validation`/`StoryRepairer`/`TurnCommitter`），定义在 `core::turn_pipeline`。所有 Pipeline 与 `aise-server` SSE 事件已改用该枚举。

`TurnRuntime::run` 会记录 `StageStarted` 和 Pipeline Trace，根据 `Ok` / `Err` 写入 `PipelineData`，随后通过 `outcome?` fail-fast。

当前 `AiseError` 包含 StoryNotFound、LLM、Store、Migration、I/O、JSON、ValidationBudgetExhausted、InvalidRequest、InvariantViolation 和 Internal。设计要求的 ValidationRejected、TurnDeadlineExceeded、Cancelled、RevisionConflict、IdempotencyConflict、Backpressure 尚未形成独立错误类型。

## 7. TurnExecutionContext 与预算

当前 Context 字段（全部私有，定义在 `core::turn_context`）：

```text
identity / phase / player_input / baseline_ctx / plan
retrieved_ctx / character_thoughts / proposal / validation
budget / control / trace / committed_result
```

Phase 1 已完成的状态：

- 字段全部私有化，只有业务语义写方法（`set_prepared_context` / `set_writer_plan` / `set_retrieved_context` / `set_character_thoughts` / `set_story_proposal` / `set_validation_result` / `set_committed_result`）和只读 getter。
- 加入 `TurnPhase` 状态机（`Preparing` → `Prepared` → `Committed`，`ReadyToCommit` 为写提交结果的门禁 Phase）；非法跳转返回 `InvariantViolation`。
- `TurnExecutionContext::new` 现在要求调用方先构造有效 `TurnIdentity`、`TurnRequest`、`TurnBudget`、`TurnControl` 和 `TraceRecorder`；`turn_id` 由 Engine 在创建 Identity 时生成，不再有半初始化状态。初始值来源：`BaselineContextBuilder` 通过 `ctx.story_id()` 读取，不再由 Context 猜测。

仍待后续 Phase：

- 无 `StoryReadSnapshot`、`base_revision`、`ValidatedChangeSet`。
- `TurnControl`（deadline + CancellationToken）与 `committed_result` 已存在但 Runtime 尚未消费 deadline/取消。

当前 `TurnBudget` 定义（`core::turn_budget`）：

- `max_repair_rounds = 3`。
- `max_tokens = 2048`。
- `max_retrieved_items = 20`。

Phase 1 后由 `AiseEngine` 从 `TurnConfig` 构造单一 `TurnBudget` 放入 Context，Pipeline 不再保存重复的 `max_tokens`。`max_retrieved_items` 已用于历史加载和 Retrieval。`max_repair_rounds` 尚未接入控制流。当前没有总 token 计数、deadline、单次 timeout、取消信号或 LLM 预算 reservation。

## 8. Context、Planning、Character 与 Story

### 8.1 Baseline Context

`BaselineContextBuilder` 当前调用：

- `Store::load_characters`。
- `Store::load_story`。

它填充 player character、relevant characters 和 recent story。World、Memory、Story Instructions、Current Scene、Summary 和 Constraints 尚未加载，也没有统一 revision snapshot。

### 8.2 Writer Planner

当前 Planner 不调用 LLM。它把 `player_input` 复制到 `StoryGoal.summary`，Retrieval 与 Character Think 是否执行由请求集合是否为空决定（Retrieval Pipeline 检查 `plan.retrieval_requests`，Character Think 检查 `plan.character_think_requests`）。v3.1 要求的 `need_*` 布尔值已删除，计划状态不再可能与请求集合矛盾。

### 8.3 Context Retrieval

当前 Retrieval 只把 recent story 转换为 `HistoricalStory` 类型的 `ContextItem`。尚未接入 Character Memory、World Knowledge、Narrative Graph 或 Lore Book，也没有 Context Merger、来源权限和 token 合并策略。

### 8.4 Character Think

当前 Character Think 不调用 LLM。需要执行时只按请求角色生成占位 Thought，并把 player input 复制到 perception。

### 8.5 Story Generator

当前 Generator 只把 player input 作为单条 user message 发送给 LLM，没有组合 Baseline Context、WriterPlan、Retrieved Context 或 Character Thoughts。

Generator 生成 Story Text 和一个 Action Event；Character、World、Memory updates 为空。调用为非流式 completion。

## 9. Validation 与 Repair

当前 `ValidationPipeline` 依次运行：

- `SchemaValidator`：仅检查 Draft 是否存在以及 Story Text 是否为空。
- `ConsistencyValidator`：当前固定返回通过。

`ValidationIssue` 当前具有 severity、code 和 message，尚无 repairability 和 location。

关键差距：Validation 不通过时 Pipeline 仍返回 `Ok(())`，但 `TurnCommitter` 现在检查 `ctx.phase() == TurnPhase::ReadyToCommit`，未通过验证的 Turn 会在提交门禁处得到 `InvariantViolation` 并整体失败——"未通过验证不得提交" 已由 Phase 门禁兜底（而非由 Validation 决策枚举驱动，后者属 Phase 3）。

`StoryRepairer` 当前为 no-op，没有装配。`max_repair_rounds` 和 `ValidationBudgetExhausted` 已定义但未接入。

---

## 10. 提交与持久化

### 10.1 已实现行为

`TurnCommitter` 持有 `Arc<dyn Store>`，从 `ctx.proposal()` 构造 `TurnCommit`，并在 `ReadyToCommit` Phase 门禁下执行（非该 Phase 返回 `InvariantViolation`）。`SqliteStore::commit_turn` 使用一个 SQL transaction 写入：

- World。
- Story Turn。
- Story Events。
- Characters。
- Memory。

单数据库事务原子性已经具备。

### 10.2 与设计的差距

- Committer 直接接受未转换的 `StoryProposal`，没有 `ValidatedChangeSet`。
- 当前只实际提交 Story Turn 和 Events；Character、World、Memory 与 Summary 输入为空。
- 没有 Story revision 和 compare-and-swap。
- 没有请求幂等键和返回原 Turn 的恢复协议。
- 没有 Outbox 和派生状态消费者。
- 没有明确 Commit marker 或 Turn 恢复状态。

当前还有一个需要优先修正的语义问题：`TurnCommit.world == None` 会被 `SqliteStore` 转换为空 `WorldState` 后执行 upsert，而不是“不修改 World”，可能覆盖已有 World 内容。

## 11. 结果、SSE 与任务生命周期

`AiseEngine::run_turn` 在 Runtime 成功后发出：

```text
TurnEvent::Validation
TurnEvent::Token
TurnEvent::Finished
TurnEvent::Trace
```

`Token` 当前是完整 Story Text，不是 LLM delta。由于 Committer 是末尾 Pipeline，成功事件在提交完成后发出，这一点符合设计。

差距：

- Runtime 失败时只产生 Trace，HTTP 后台任务记录错误；SSE 客户端没有显式失败终态。
- `CommittedTurnResult` 只有 turn_id 和 story_text，没有 committed revision。
- `SseSink` 使用 unbounded channel，没有背压。
- SSE 发送失败和 Trace JSON 序列化失败被忽略。
- `tokio::spawn` 的 Turn 任务没有明确 owner、取消或 shutdown 等待协议。

## 12. LLM、Trace 与容量

### 12.1 LLM

应用组合根创建共享 `LlmLimiter` 并注入 `OpenAiCompatProvider`。Provider 的 completion 和 streaming 都会先获取 semaphore permit，符合共享并发限制设计。`StoryGenerator` 直接持有 `Arc<dyn LlmProvider>` 并在 Pipeline 内自行完成 `Instant`、`tracing::info_span!`、`LlmCallData` 拼装和 trace begin/end。

v3.1 差距：

- 不存在 `LlmGateway`；所有 Pipeline 仍直接持有 `LlmProvider`。
- v3.1 要求 Provider 只处理供应商协议（构建 HTTP 请求、解析响应/SSE/finish reason/usage），不得持有 Limiter；当前 Limiter 在 Provider 内部。
- limiter 等待 timeout 未实现。
- Turn deadline 和取消传播未实现。
- embedding 接口及其并发限制未实现。
- token 实际消费统计、usage 结算、计费和 Gateway 统一 tracing 未实现。
- LLM tracing 内容策略未统一；当前由调用方拼接 prompt/response 文本。

### 12.2 Trace

`TraceRecorder` 默认最多保存 64 spans，超出后记录 `dropped_span_count`。定义已迁入 `core::turn_trace`，类型包括 `TurnTrace`、`TraceSpan`、`SpanPayload` 及 `LlmCallData`、`PipelineData`、`StoreCallData`、`ValidationData`、`PersistData`。当前已记录 Turn、Pipeline、LLM Call、Store Tool Call、Validation 和 Persist。

Prompt 与 Response 分别限制为 2000 和 4000 字符。仍需补充隐私分类和敏感内容清理策略。

### 12.3 已有容量边界

- `SessionRegistry.capacity`。
- `TurnBudget.max_retrieved_items`。
- `LlmLimiter` semaphore。
- Trace span 数量限制。
- LLM Trace 文本截断。

尚未受控的主要资源包括 HTTP Turn task、SSE channel、角色/世界集合、Validation Issues、持久化历史和派生任务。

## 13. 优先差距

### P0

1. Validation 失败不会阻止 Commit。
2. `TurnCommit.world == None` 可能以空 World 覆盖已有状态。
3. 直接调用 `AiseEngine::run_turn` 可以绕过同 Story 串行化。
4. Repair Loop 未实现且修复预算未消费。

### P1

1. ~~v3.1 `core` Turn Contracts 层不存在，`TurnExecutionPipeline` 等仍定义在 `runtime`。~~ → 已解决（Phase 1）：`core` 层建立，Contracts 全部迁入，旧路径删除。
2. Runtime 未强制固定工作流拓扑，仍接受任意 Pipeline Vec（`TurnPipelineSet` 属 Phase 5）。
3. ~~Context 缺少私有字段、阶段状态机、有效构造和写权限边界。~~ → 已解决（Phase 1）。
4. 缺少 Story revision、幂等提交和崩溃恢复协议。
5. `StoryDraft` 已迁移为 `StoryProposal`（Phase 1），但 `ValidatedChangeSet` 领域授权边界仍未实现（Phase 3）。
6. 缺少统一 `LlmGateway`；Pipeline 直接持有 `LlmProvider`，Provider 仍持有 Limiter（Phase 2）。
7. Turn 任务与 SSE channel 缺少背压、取消和 shutdown 协议（Phase 2/5）。
8. `TurnBudget` 已统一为配置生成的单一实例（Phase 1），但无 LLM token 预算 reservation（Phase 2）。
9. Context、Planner、Character Think、Validation 仍主要是骨架实现。

## 14. 维护规则

- `Architecture.md` 只描述最终架构，不记录实现进度。
- 本文只记录实现映射和差距，不改变架构决策。
- 新增与设计同义的组件前，先确认现有类型是否已经拥有该职责。
- 代码实现某项差距后，应更新本文对应状态和说明。
- 如果实现需要偏离 `Architecture.md`，必须先完成架构评审并更新设计文档，不能只修改本文来迁就代码。
